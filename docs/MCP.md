# Authenticated MCP interface

AIMuse binds only to `127.0.0.1` on a private port in the `48300–48331` range. Every MCP request requires `Authorization: Bearer <token>`. Tokens are random, stored with Electron `safeStorage` (Windows protected storage or the macOS Keychain-backed adapter), compared in constant time, and never accepted in a URL. The health endpoint is intentionally non-sensitive.

Start a private headless engine with an absolute connection-file path:

```powershell
AIMuse.exe --headless --write-mcp-connection=C:\private\aimuse-mcp.json --authority-policy=C:\private\authority.json
```

```sh
./AIMuse.app/Contents/MacOS/AIMuse --headless --write-mcp-connection=/absolute/owner-private/aimuse-mcp.json --authority-policy=/absolute/owner-private/authority.json
```

The caller must create the parent as an owner-only operating-system directory before launch. On Windows, remove inherited broad-group access and retain only the launching user, SYSTEM and Administrators; Node's `0o600` creation mode is not a substitute for that ACL. On macOS, every existing component below the private root must remain owned by the launching user with group/world mode bits clear; the QA harness creates cycle directories as `0700` before writing a bearer. General QA coordination requires this existing directory explicitly as `--private-root` for session start/MCP initialization and every follow-up. Coordinator manifest/state persist only its non-secret canonical filesystem identity; follow-ups reject permission/ownership, link, containment or directory-object drift before bearer, request or evidence activity. Re-read the connection after every restart because the protected localhost bearer may rotate.

The atomic connection file has this shape:

```json
{
  "version": 1,
  "url": "http://127.0.0.1:48000/mcp",
  "token": "private bearer token",
  "activeProjectId": "project_...",
  "pid": 1234,
  "instanceId": "11111111-1111-4111-8111-111111111111",
  "profileId": "0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF",
  "trustedFolders": []
}
```

`instanceId` is a fresh non-secret UUID for one engine process. `profileId` is a non-secret SHA-256 identity for the normalized local user-data path; the raw profile path is not exposed by health. QA coordination binds connection, health, manifest, show, stop and redaction evidence to these identities before touching a process or requesting a window.

## Client setup

The editor’s **Agents → Connect an external agent** flow has first-class profiles for Codex, Claude Code, OpenCode and Antigravity, plus a generic Streamable HTTP profile. Automatic setup always shows a native confirmation before writing. It names the target configuration, explains that the private bearer will be stored there, creates a timestamped backup when the file already exists, and replaces only the `aimuse` MCP entry. Unrelated settings and MCP servers are preserved; malformed JSON/JSONC is rejected without overwriting the file. A successful automatic setup also enables the headless AIMuse engine at sign-in.

| Client | User configuration written | AIMuse entry |
| --- | --- | --- |
| Codex | `$CODEX_HOME/config.toml` or `~/.codex/config.toml` | `[mcp_servers.aimuse]` with `url` and an Authorization `http_headers` value |
| Claude Code | `~/.claude.json` | `mcpServers.aimuse` with `type: "http"`, `url`, and Authorization header |
| OpenCode | `$XDG_CONFIG_HOME/opencode/opencode.json[c]` or `~/.config/opencode/opencode.json[c]` | Stable `mcp.aimuse`, or `mcp.servers.aimuse` when that V2 wrapper already exists; comments and sibling servers remain |
| Antigravity | `~/.gemini/config/mcp_config.json` | `mcpServers.aimuse` with `serverUrl` and Authorization header |

The generic profile performs no file write and instead displays exact `transport: "streamable-http"`, URL, and header settings for copying. Treat every generated client config or snippet as a credential-bearing file, and restart or reconnect the selected client after setup.

## Health and show acknowledgement

The unauthenticated, non-sensitive `/health` response includes a bounded `showAcknowledgements` array. Each record contains only a fresh show-request UUID, `pending`/`accepted`/`rejected` state, PID, engine `instanceId`, hashed `profileId`, timestamps, attempt count and—when rejected—a fixed reason. It never contains the bearer token, raw profile path, MCP session ID or project data. Pending and recent terminal records are never evicted to admit another request; ledger saturation rejects the new request, while expired terminal records may be pruned.

A receiver inserts `pending` before starting window work, then publishes `accepted` only after that exact instance/profile-bound request completes. A wrong or malformed binding is rejected; a duplicate request poisons the record as rejected rather than allowing either caller to claim success. The QA coordinator requires the request ID to be absent before launch, treats helper exit zero only as permission to poll, accepts exactly one timely same-generation acknowledgement, and re-probes the unchanged acknowledgement plus PID/health identity before setting `windowRequested`. Missing, pending-at-deadline, rejected, stale, late, duplicate or malformed evidence fails closed without a manifest update.

Clients initialize standard stateful Streamable HTTP MCP, retain the returned `mcp-session-id`, then call `session_manage.join` to provide their display name and client/model metadata. The server supports at most 32 concurrent sessions and releases capacity on MCP `DELETE`.

`transport_manage` treats `recordingSource: "midi-input"` as explicitly unavailable until a native MIDI backend is connected. It returns `midi_input_unavailable` before policy/approval, job creation or transport state can imply capture. MIDI input permission remains a required future authority gate, but it is not proof that a backend, port, timestamp, capture stream or take mutation exists. The native hello/controller discovery status is intentionally not a capture grant: a future backend may report only opaque direction-qualified IDs, and an endpoint operation must re-check its discovery generation after authorization so disconnect/reconnect cannot reuse a stale reference. The current status is disconnected with no ports; no MCP port-list/open/send/capture contract exists yet. Microphone recording retains its separate policy/approval contract.

Cold clients do not need repository documentation. Initialize returns concise cross-tool instructions; `tools/list` exposes described inputs/outputs plus action-specific `oneOf` branches for conditional requiredness; every incomplete or job-returning call includes explicit `next` guidance. Call `aimuse_help` for focused workflow/privacy topics. Clients that support resources can additionally read the complete `aimuse://guide`, but correctness never depends on instructions, prompts or resources being rendered.

`project_apply` SFX-deliverable add/update/delete operations and those service-produced records cross the same canonical reducer boundary as other direct project edits. A `track.move` that would place a folder beneath its descendant is rejected before project mutation, and the same reciprocal hierarchy cycle is rejected when encountered in stored state. This is only the already-declared track-hierarchy rule: clients must not infer a policy for audio-output, send or device-routing cycles, hierarchy deletion/retention, migration or repair.

Direct and branch `project_apply`, `history_manage` undo/redo, `project_manage` checkpoint/branch/merge/discard, `generation_manage` start/variation/accept/reject, `plugin_manage` parameter/preset/bypass/remove, WAV `media_manage analyze`, and `media_manage` audition/consolidation render-job creation pass through four shared admission lanes; variant compare, generation capabilities/inspect, plug-in catalog and media listing remain observations that bypass them. A request can start immediately while a lane is free; actor round-robin governs work after it is queued. Actual first queued arrival establishes the actor rotation, and later work for an already queued actor remains FIFO rather than reseeding it. Each actor can queue at most four mutations and the global queued cost is 2,048. A project transaction costs its operation count; each history, checkpoint/variant, generation, plug-in device, media-analysis or media-render-job creation action costs one. Overflow returns `status: "busy"` with `actor_queue_full` or `global_queue_full`, a bounded retry delay, queue depths and explicit next-step guidance; it does not mutate the project. These domain/history actions are not generally idempotent, so their busy/cancelled guidance requires owned-job inspection where applicable plus project re-observation before the caller decides whether to issue another action rather than instructing a blind retry.

Closing an MCP session cancels that actor’s queued work and removes its presence, while **Stop agents** cancels matching queued project work. A deliberate session DELETE closes the response transport too, so its safety contract is queue/effect cleanup rather than delivery of cancellation bodies for already-outstanding calls. DELETE does not itself invoke `job_manage cancel` for already-created owner jobs; cancel those explicitly before deleting the session when that is the desired outcome. Automatically cancelling every producer job on DELETE is not promised because their running partial effects and future ownership/resumption policy are not one cross-family contract. Queued history or checkpoint/variant cancellation occurs before the corresponding service method is invoked; for checkpoint/variant work this also precedes snapshot-file creation. Queued generation start/variation cancellation occurs before approval reservation, job creation, credential/provider work or provider request; queued accept/reject cancellation occurs before candidate disposition, asset-source registration or project mutation. Queued plug-in parameter/preset/bypass/remove cancellation occurs before any project transaction. Queued WAV analysis occurs before its registered source is read, before any managed-cache output and before its project transaction. Queued audition/consolidation cancellation occurs before job creation, render invocation, cache output and project transactions. Already-running admission work is not preempted, and the project service continues to serialize commits to the same project. An admitted generation or media-render start creates its owner-only job and then releases the mutation lane; potentially long provider or render execution is controlled by `job_manage` and does not monopolize project admission. This deliberately rejects holding a scheduler lane for the job runtime, which would starve ordinary project edits and duplicate the existing owner-job lifecycle.

A started checkpoint writes its validated content-addressed snapshot before registering it; a started branch commits its base checkpoint before registering the variant, so a later failure preserves that existing partial-commit boundary. Merge retains its atomic graph/journal commit and discard retains its revision-checked transaction semantics. Generation acceptance retains its existing asset-source-before-project-commit boundary and updates the owned job’s accepted IDs only after a committed project transaction; duplicate acceptance returns `duplicate`, while rejection retains immutable candidate media and de-duplicates the rejected ID. Each admitted plug-in parameter, preset, bypass or removal action is exactly one revision-checked project transaction, so locks or revision conflicts commit nothing and a successful transaction remains atomic. Running WAV analysis writes three content-addressed cache outputs before one atomic three-asset project transaction; completed cache files can remain after a later write or commit failure, but a rejected transaction registers no project assets or sources. Running media-render cancellation is terminal for its owner job but cooperative: it neither preempts the render function nor rolls back an already-started project transaction. A late render can retain a managed-cache WAV with no project change, an in-flight asset transaction can commit and register its source, and an in-flight consolidation clip transaction can also commit. Cancelled and failed jobs report `partial.cache` as `retained` or `may-be-partial` and `partial.project` as `unchanged`, `asset-committed` or `asset-and-clip-committed`; a non-cancelled exception remains a retryable failed job. Plug-in scan keeps its catalog-job lifecycle and authority-gated instantiate keeps its approval continuation; scheduling either as though it were an ordinary atomic device edit was rejected.

Plug-in scan has a producer-specific terminal contract. Owner cancellation can occur before discovery, while an injected/native helper call is outstanding, or during final atomic catalog persistence; no late path may overwrite `cancelled` with `completed` or `failed`. Owner-only `result.partial` reports `discovery` (`not-started`, `may-have-completed`, `completed`), `nativeHelper` (`not-started`, `unconfirmed`, `settled`), `candidateResults` (`none`, `partial`, `complete`) and `catalog` (`unchanged`, `write-may-have-completed`, `replaced`) plus candidate/result counts. Candidate descriptors remain private scan-local work until the complete replacement is persisted, so cancellation during discovery or candidate processing leaves the old global catalog and never publishes a partial prefix. Cancellation during persistence is cooperative: inspect again because a resolved atomic write retains and publishes the complete replacement, while a rejected atomic write settles unchanged. A successful zero-candidate scan still replaces the catalog with an empty catalog. `nativeHelper` does not promise process preemption, cleanup or visibility into plug-in side effects, even after the call settles. AIMuse does not retry automatically. Re-read the global catalog and inspect the owner job before deciding whether to scan again. The deterministic listener uses injected discovery/scanner/writer seams and executes no native helper, so native cancellation/preemption remains a separate acceptance boundary; instantiate remains a separate authority/approval producer.

The injected-provider, render, export and save listeners retain their producer-specific boundaries; open adds waiting zero effects, direct-authority no-job compatibility and exact/conservative workspace-controller settlement; unpack adds archive-open/entry-write/removal injection, sequential partial output, later open effects and status monotonicity; scan adds empty/last-candidate/final-write terminality and global catalog re-observation; instantiate adds waiting zero effects, direct allowlist compatibility, destination-lock/current-target validation and late commit/failure monotonicity; import adds waiting zero effects, direct-authority compatibility, sequential cache/transaction/warning partials, late copy/engine-error/preparation-rejection monotonicity and ordinary failure/no retry. Save, open, scan, unpack, instantiate and import listeners also pass in eight independent processes, totaling twenty-four, thirty-two, thirty-two, forty-eight, thirty-two and forty race-test executions respectively. None calls `audio.start()` or launches native helpers; actual native-helper scan cancellation/preemption, recording and other generic approved-action producers, native SDK-backed instantiate/hosting and session ownership remain separate.

`project_manage close` treats dirty-project recovery as part of the close transaction. With `force:false`, a dirty project remains unchanged and returns exactly `{ "closed": false, "reason": "Project has unsaved changes." }`. With `force:true`, AIMuse first awaits durable removal of that project's recovery subject and only then removes the in-memory project and returns `{ "closed": true }`. If durable removal fails, the call rejects and the project remains open; a success response may never precede recovery invalidation. A later same-profile restart therefore cannot restore the explicitly discarded ID, while other unclosed dirty projects retain normal crash-recovery behavior. This is not a permanent ban on the project ID: a separately saved project may still be explicitly reopened through the ordinary controlled file boundary.

Active human entity and timeline-range locks are enforced before an authenticated agent transaction is reduced. Timeline drags acquire a renewable 10-second `phase: "gesture"` lease while the pointer remains active. Completing a drag converts that lease into a visible, non-refreshable 15-second `phase: "grace"` lock so an agent can observe and defer to the just-completed human edit; the user can end it immediately with **Release now**. Main-process expiry timers, renderer cleanup and lazy admission-time expiry bound the lock even if the renderer disappears. A conflicting `project_apply` returns `status: "locked"` with the fixed human-edit message and `conflict.retryable: true`, leaves the project unchanged, and includes `conflict.entityId` only when the lock identifies one. Lock admission precedes revision validation, so a stale colliding edit reports `locked` during grace and reverts to an ordinary stale `conflict` after release or expiry. Unrelated operations remain eligible to commit while the lock is held.

`trace_replay` requires an open `projectId` and a `transactionId` present in that project's durable trace. It invokes the same bounded trace-progress route used by the desktop preload API, but never reapplies the transaction, creates a revision, changes actor history, writes a checkpoint, or performs file I/O. The credential-free receipt binds the trace resource, source revision/outcome/actor, full trace-entry and transaction SHA-256 values, ordered operation kinds and progress steps to canonical before/after revisions and SHA-256 values; selected-trace drift during replay fails closed. `status: "completed"` with `canonical.unchanged: true` proves that canonical state remained identical; a concurrent external edit is reported as `status: "concurrent-change-observed"`, never mislabeled as an unchanged replay. Full operation bodies remain in the authenticated trace resource rather than being copied into the receipt.

Public job data is owner-scoped at every tool and resource boundary. A session cannot list, inspect, wait on, obtain an approval dependency for, cancel, vary, accept or reject another authenticated actor's job. `aimuse://sessions` retains shared authenticated presence but filters job summaries to the exact reader; `aimuse://jobs/{id}` and job-oriented tools make a foreign ID indistinguishable from a missing ID. Waiting summaries may include approval request details only for the owner.

Approval-capable requests share one global exact-job reservation across the engine. The reservation is acquired before authority-dependent request preparation, so only one `waiting-for-user` approval can be published. A concurrent approval-capable MCP request performs no file, provider, plug-in or other protected I/O, creates no job and returns exactly `{ "error": "approval_pending", "retryable": true, "message": "Another approval-capable request is being prepared or awaits human review. No job was created." }`. It returns no `jobId`, incumbent actor, destination/path or request details. As defense in depth, the central job store converts any attempted second `waiting-for-user` publication into the same failed `approval_pending` outcome. The reservation is released after the approval leaves `waiting-for-user` or is cancelled; failure paths cannot strand it.

MCP exposes no approval action. A waiting job's `next` field says that a human must review it in AIMuse and suggests a bounded owner-only `job_manage wait`; helper exit, polling or a successful MCP call never grants authority. An out-of-root save creates only that owner job and performs no file write. Formal QA uses an even stricter sequence: submit one approval-capable request, resolve it natively, wait for its exact job to become terminal, prove the global/native pending count is zero, and only then submit the next request.

For an approved project open, owner cancellation immediately releases approval capacity and cannot be overwritten by later completion or failure. Waiting cancellation performs no read. A returned open reports exact retained or unchanged workspace/project/controller effects; a rejected open remains conservative and requires workspace re-observation. No rollback, preemption or retry promise is made. Foreign and missing IDs remain indistinguishable.

For an approved project unpack, owner cancellation immediately releases approval capacity and cannot be overwritten by later extraction/open completion or failure. Waiting cancellation has zero archive/destination/open effect. Running results remain producer-specific and bounded: entry counts and destination/removal state preserve sequential partial output, while validated extraction and later workspace/controller effects remain independently re-observable. No archive-wide atomicity, cleanup, rollback, preemption, retry or fair-lane promise is made. Foreign and missing IDs remain indistinguishable.

For an approved project save, owner cancellation immediately releases approval capacity and cannot be overwritten by the continuation's later completion or failure. Waiting cancellation is zero-effect. Running cancellation is cooperative and exposes only producer-specific destination/project/audit partials; no atomic all-files, preemption, cleanup or retry promise is made. Foreign and missing IDs remain indistinguishable, and any late successful `file.saved` record retains the server-authenticated actor.

A successful `project_manage save` carries the server-authenticated actor through the save boundary and returns a `file.saved` audit record. The same destination-free record is atomically retained in `activity/file-audit.jsonl` and can be requested with `project_observe.includeFileAudit`. It contains only event version/ID/type, project ID, actor, timestamp and `succeeded`; it is separate from reducer activity/transaction trace, does not increment revision, does not create an undo step and never publishes the destination or approval request.
