# Authenticated MCP interface

AIMuse exposes a stable product-owned stdio bridge to configured MCP clients. Internally, the current engine binds only to `127.0.0.1` on a private port in the `48300–48331` range. Every HTTP request—including health—requires a fresh random 32-byte engine bearer. The listener first requires a well-formed nonempty authority and compares it in constant time, never accepts it in a URL, and discards it on stop. Every admitted request is bound to the current authority/admission generation. A POST revalidates that binding after its complete body arrives, before parsing or route/session lookup, and again immediately before allocation or transport handling. Stop closes admission synchronously, so a slow request authenticated before shutdown, as well as absent, blank, invalid, wrong and formerly valid authority arriving afterward, receives only the authentication rejection while pending cleanup delays socket closure. The bearer is not part of client configuration, renderer/preload IPC, or ordinary user workflow, and no TCP endpoint is usable without authentication.

Launch the app normally or start the same canonical runtime headlessly:

```powershell
AIMuse.exe
AIMuse.exe --headless --authority-policy=C:\private\authority.json
```

```sh
./AIMuse.app/Contents/MacOS/AIMuse
./AIMuse.app/Contents/MacOS/AIMuse --headless --authority-policy=/absolute/owner-private/authority.json
```

GUI and headless startup both atomically publish one internal run-state record below the profile's dedicated `mcp-runtime` directory only after the authenticated listener is ready. The record is bound to the current PID, fresh engine `instanceId`, hashed profile identity, exact loopback URL and engine bearer. On POSIX the directory/file are owner-only `0700`/`0600`; on Windows AIMuse removes inherited access and permits only the launching user, SYSTEM and Administrators. Linked, malformed, wrong-profile, dead-PID, health-mismatched, stale and ambiguous records grant no authority. Clean stop removes only its exact matching record before closing the listener. Dead-PID crash residue is useless and replaceable because the listener and bearer died with the engine; a still-live recorded PID whose authenticated identity cannot be verified blocks publication instead of being guessed stale.

## Client setup

The editor’s **Agents → Connect an external agent** flow has first-class one-time stdio profiles for Codex, Claude Code, OpenCode and Antigravity, plus a generic stdio profile. The displayed snippet contains only the installed AIMuse executable, `--mcp-bridge`, and `--mcp-target-profile=<stable engine profile>`. It contains no Chromium `--user-data-dir`, URL, bearer, PID, instance ID, account credential, or other per-launch value. Before Electron receives browser state, the entry disables bridge hardware acceleration, prohibits macOS activation, derives a deterministic sibling, requires a real link-free directory (owner-private on POSIX), rejects canonical-path and filesystem-ID equivalence with the target (including Windows case/reparse/junction aliases), and revalidates both identities immediately after `app.setPath`. An unsafe or malformed entry exits immediately and cannot fall through to engine-profile installation. AIMuse does not locate, back up, or modify a client configuration file and does not enable sign-in startup as a side effect. Source tests bind this wiring; a fresh relocated arm64 development package additionally passed a real stdio-client headless lifecycle and exact-package alias/process checks. Visual no-Dock/UI, interactive GUI, Windows and distribution acceptance remain open.

Copy the snippet once and perform the client's one initial reconnect if it requires one. Thereafter the configured client launches the AIMuse-owned bridge. A bridge started before AIMuse waits without opening an unauthenticated listener; after the user launches the GUI or supported headless engine, it privately discovers and authenticates the exact instance. When the engine restarts, the same bridge configuration creates a fresh internal MCP session against the new authority without a settings visit, configuration rewrite, password, Keychain access, or manual token transfer.

The explicit `--write-mcp-connection=<absolute path>` switch remains test-harness coordination only. It is not generated by client onboarding, is not a durable client configuration, and must remain inside the formal owner-private QA root with cleanup/redaction. Product clients use the stdio bridge.

## Health and show acknowledgement

The bearer-authenticated `/health` response includes a bounded `showAcknowledgements` array. Each record contains only a fresh show-request UUID, `pending`/`accepted`/`rejected` state, PID, engine `instanceId`, hashed `profileId`, timestamps, attempt count and—when rejected—a fixed reason. It never contains the bearer token, raw profile path, MCP session ID or project data. Pending and recent terminal records are never evicted to admit another request; ledger saturation rejects the new request, while expired terminal records may be pruned.

A receiver inserts `pending` before starting window work, then publishes `accepted` only after that exact instance/profile-bound request completes. A wrong or malformed binding is rejected; a duplicate request poisons the record as rejected rather than allowing either caller to claim success. The QA coordinator requires the request ID to be absent before launch, treats helper exit zero only as permission to poll, accepts exactly one timely same-instance acknowledgement, and re-probes the unchanged acknowledgement plus PID/health identity before setting `windowRequested`. Missing, pending-at-deadline, rejected, stale, late, duplicate or malformed evidence fails closed without a manifest update.

Clients initialize standard MCP over stdio and then call `session_manage.join` to provide their display name and client/model metadata. The bridge privately initializes the current stateful Streamable HTTP session, retains its `mcp-session-id`, forwards notifications, and repeats that internal initialization when engine identity changes. If the same session's notification GET ends cleanly or errors, its liveness marker clears and the next serialized client message opens exactly one replacement GET without replacing the valid POST session. Close invalidates the lifecycle, aborts discovery/notification I/O, waits for admitted bounded POST work and DELETEs a session returned by a late initialize response; it does not hide a possibly allocated session ID by close-aborting that initialize POST. The server supports at most 32 committed-plus-pending sessions: initialization reserves capacity before allocation, failed/aborted/unadopted sessions close exactly once, MCP `DELETE` releases adopted capacity, and host stop invalidates and awaits every pending allocation before returning.

`transport_manage` treats `recordingSource: "midi-input"` as explicitly unavailable until a native MIDI backend is connected. It returns `midi_input_unavailable` before policy/approval, job creation or transport state can imply capture. MIDI input permission remains a required future authority gate, but it is not proof that a backend, port, timestamp, capture stream or take mutation exists. The native hello/controller discovery status is intentionally not a capture grant: Windows source can now watch its MIDI selectors using opaque direction-qualified `DeviceInformation.Id` identities, but the shared registry remains empty until both direction scans complete and status fails disconnected if either watcher stops. Watcher lifetime remains separate from endpoint use. An endpoint operation must re-check its discovery generation after authorization so disconnect/reconnect cannot reuse a stale reference. There is still no MCP port-list/open/send/capture contract, and this source wiring is not Windows-device acceptance. Microphone recording retains its separate policy/approval contract.

Cold clients do not need repository documentation. Initialize returns concise cross-tool instructions; `tools/list` exposes described inputs/outputs plus action-specific `oneOf` branches for conditional requiredness; every incomplete or job-returning call includes explicit `next` guidance. Call `aimuse_help` for focused workflow/privacy topics. Clients that support resources can additionally read the complete `aimuse://guide`, but correctness never depends on instructions, prompts or resources being rendered.

Direct and branch `project_apply`, `history_manage` undo/redo, `project_manage` checkpoint/branch/merge/discard, `plugin_manage` parameter/preset/bypass/remove, WAV `media_manage analyze`, and `media_manage` audition/consolidation render-job creation pass through four shared admission lanes; variant compare, plug-in catalog, and media listing remain observations that bypass them. A request can start immediately while a lane is free; actor round-robin governs queued work. Each actor can queue at most four mutations and global queued cost is 2,048. Overflow returns a bounded `busy` result without mutation. Re-observe state before repeating a non-idempotent action.

Closing an MCP session cancels that actor’s queued work and removes its presence, while **Stop agents** cancels matching queued project work. Session DELETE does not cancel already-created owner jobs; cancel those explicitly when desired. Queued checkpoint/variant, plug-in, WAV-analysis, and media-render admission is cancelled before its corresponding domain effect. Already-running work is cooperative and remains subject to producer-specific partial-effect reporting.

A started checkpoint writes its validated content-addressed snapshot before registration; a started branch commits its base checkpoint before variant registration. Plug-in device edits remain revision-checked project transactions. WAV analysis writes content-addressed cache outputs before one atomic asset transaction, and running audition/consolidation cancellation remains cooperative: a late cache or project effect is reported through the owner job rather than hidden. Plug-in scan and authority-gated instantiate retain their producer-specific job contracts.

Plug-in scan has a producer-specific terminal contract. Owner cancellation can occur before discovery, while an injected/native helper call is outstanding, or during final atomic catalog persistence; no late path may overwrite `cancelled` with `completed` or `failed`. A successful zero-candidate scan still replaces the catalog with an empty catalog. `nativeHelper` does not promise process preemption, cleanup or visibility into plug-in side effects, even after the call settles. The deterministic listener uses injected discovery/scanner/writer seams and executes no native helper, so native cancellation/preemption remains a separate acceptance boundary; instantiate remains a separate authority/approval producer.

`project_manage close` treats dirty-project recovery as part of the close transaction. With `force:false`, a dirty project remains unchanged and returns exactly `{ "closed": false, "reason": "Project has unsaved changes." }`. With `force:true`, AIMuse first awaits durable removal of that project's recovery subject and only then removes the in-memory project and returns `{ "closed": true }`. If durable removal fails, the call rejects and the project remains open; a success response may never precede recovery invalidation. A later same-profile restart therefore cannot restore the explicitly discarded ID, while other unclosed dirty projects retain normal crash-recovery behavior. This is not a permanent ban on the project ID: a separately saved project may still be explicitly reopened through the ordinary controlled file boundary.

Active human entity and timeline-range locks are enforced before an authenticated agent transaction is reduced. Timeline drags acquire a renewable 10-second `phase: "gesture"` lease while the pointer remains active. Completing a drag converts that lease into a visible, non-refreshable 15-second `phase: "grace"` lock so an agent can observe and defer to the just-completed human edit; the user can end it immediately with **Release now**. Main-process expiry timers, renderer cleanup and lazy admission-time expiry bound the lock even if the renderer disappears. A conflicting `project_apply` returns `status: "locked"` with the fixed human-edit message and `conflict.retryable: true`, leaves the project unchanged, and includes `conflict.entityId` only when the lock identifies one. Lock admission precedes revision validation, so a stale colliding edit reports `locked` during grace and reverts to an ordinary stale `conflict` after release or expiry. Unrelated operations remain eligible to commit while the lock is held.

`trace_replay` requires an open `projectId` and a `transactionId` present in that project's durable trace. It invokes the same bounded trace-progress route used by the desktop preload API, but never reapplies the transaction, creates a revision, changes actor history, writes a checkpoint, or performs file I/O. The credential-free receipt binds the trace resource, source revision/outcome/actor, full trace-entry and transaction SHA-256 values, ordered operation kinds and progress steps to canonical before/after revisions and SHA-256 values; selected-trace drift during replay fails closed. `status: "completed"` with `canonical.unchanged: true` proves that canonical state remained identical; a concurrent external edit is reported as `status: "concurrent-change-observed"`, never mislabeled as an unchanged replay. Full operation bodies remain in the authenticated trace resource rather than being copied into the receipt.

Public job data is owner-scoped at every tool and resource boundary. A session cannot list, inspect, wait on, obtain an approval dependency for, or cancel another authenticated actor's job. `aimuse://sessions` retains shared authenticated presence but filters job summaries to the exact reader; `aimuse://jobs/{id}` and job-oriented tools make a foreign ID indistinguishable from a missing ID. Waiting summaries may include approval request details only for the owner.

Approval-capable requests share one global exact-job reservation across the engine. The reservation is acquired before authority-dependent request preparation, so only one `waiting-for-user` approval can be published. A concurrent approval-capable MCP request performs no file, plug-in, recording, or other authority-gated I/O, creates no job and returns exactly `{ "error": "approval_pending", "retryable": true, "message": "Another approval-capable request is being prepared or awaits human review. No job was created." }`. It returns no `jobId`, incumbent actor, destination/path or request details. As defense in depth, the central job store converts any attempted second `waiting-for-user` publication into the same failed `approval_pending` outcome. The reservation is released after the approval leaves `waiting-for-user` or is cancelled; failure paths cannot strand it.

MCP exposes no approval action. A waiting job's `next` field says that a human must review it in AIMuse and suggests a bounded owner-only `job_manage wait`; helper exit, polling or a successful MCP call never grants authority. An out-of-root save creates only that owner job and performs no file write. Formal QA uses an even stricter sequence: submit one approval-capable request, resolve it natively, wait for its exact job to become terminal, prove the global/native pending count is zero, and only then submit the next request.

No rollback, preemption or retry promise is made. Foreign and missing IDs remain indistinguishable.

No archive-wide atomicity, cleanup, rollback, preemption, retry or fair-lane promise is made. Foreign and missing IDs remain indistinguishable.

Waiting cancellation is zero-effect. Running cancellation is cooperative and exposes only producer-specific destination/project/audit partials; no atomic all-files, preemption, cleanup or retry promise is made. Foreign and missing IDs remain indistinguishable, and any late successful `file.saved` record retains the server-authenticated actor.

A successful `project_manage save` carries the server-authenticated actor through the save boundary and returns a `file.saved` audit record. The same destination-free record is atomically retained in `activity/file-audit.jsonl` and can be requested with `project_observe.includeFileAudit`. It contains only event version/ID/type, project ID, actor, timestamp and `succeeded`; it is separate from reducer activity/transaction trace, does not increment revision, does not create an undo step and never publishes the destination or approval request.

## Ephemeral authority boundary

The MCP bearer is engine-scoped, not profile-scoped. A profile restart retains only non-secret project/application state and the preferred port; it receives a different bearer and engine instance. Startup and listener operation do not call macOS Keychain, Windows DPAPI, Linux secret service/libsecret, Electron `safeStorage`, or any persistent protected-secret backend.

The renderer/preload cannot request the live bearer or direct URL. Public snapshots report only bridge availability and authenticated session presence; resources, health, logs, and errors contain no authority. AIMuse never writes a generated client configuration. The private product run-state is consumed only by the AIMuse bridge and removed on clean stop; the explicit owner-private connection export remains QA-only handoff material and becomes invalid on stop/restart even if a test fails to redact it.

AIMuse exposes twelve MCP tools for deterministic DAW/project work. It has no generation tool, provider capability query, provider adapter, provider credential method, candidate-media route, source-separation adapter, or spending/generation authority budget. External agents can generate elsewhere under their own authority and then use controlled media import plus ordinary project edits. Legacy project provenance remains passive compatibility/recovery data; `ProjectService` rejects provenance registration/update/deletion and new `source=generation` assets from every live direct or branch mutation, including MCP and renderer IPC, while its snapshot-install boundary preserves the current passive map and generation-source assets.
