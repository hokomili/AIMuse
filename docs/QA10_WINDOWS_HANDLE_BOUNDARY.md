## Why the current path guard cannot close the last interval

The existing coordinator correctly revalidates ACL ownership, the launching-user/SYSTEM/Administrators allowlist, protected inheritance, links, canonical containment and canonical/device/inode identity before every sensitive boundary. It also makes the first validation failure sticky. A path can still be replaced after the last observation and before the following path-based filesystem or process/network call.

Holding only the root directory is insufficient. Connection and state files deliberately rotate through atomic replacement, while descendant files or stages can be independently swapped. Closing the interval therefore requires both a root lease and mediated descendant operations; merely adding another `lstat`, `realpath` or `Get-Acl` call does not change the race.

## Contract captured by the prototype

[`qa-private-root-lease-contract.mjs`](../scripts/qa-private-root-lease-contract.mjs) is an injected orchestration contract only. With no provider it fails before the operation with an architecture-review error. It preserves the existing path verifier as a mandatory preflight and requires persisted root identity, so legacy state still fails closed.

An approved provider must supply all of these capabilities as one lease:

1. Hold the exact root directory object for the complete command and deny delete/rename sharing while allowing existing read/write behavior.
2. Derive final path, file identity, reparse metadata and the security descriptor from the open handle. The owner must be the launching user; the DACL must be protected, Allow-only, owner-FullControl, and limited to that user, SYSTEM and Administrators.
3. Recheck the held handle before and after the existing path verifier. Any handle or path failure becomes sticky for the command.
4. Open every credential/evidence read as a fresh handle-validated snapshot, validate final containment and non-reparse identity before returning bytes, and never cache a connection snapshot. This preserves bearer rotation/re-read semantics.
5. Stage, flush and validate in the held target parent, then rename the staged handle to the exact fully qualified destination reconstructed from that pinned parent. The Win32 call must receive neither a process-relative name nor an unvalidated pathname, and commit metadata must remain credential-free.
6. Mediate sensitive process, health, window, signal, request and output actions between handle/path guards without exposing a raw handle to coordinator code.
7. Close exactly once. An ambiguous close is reported, not retried as if known-safe.

The contract uses an exact path allowlist. Its descriptor and operation metadata reject token, authorization, session and other private fields. Snapshot bytes may contain the live protected bearer because callers need it, but those bytes never enter descriptor/evidence output.

## Approved provider-only prototype

`native/src/qa_private_root_provider.cpp` implements the corrected opt-in addon boundary. It opens the root and every allowlisted parent with `CreateFileW` and without delete sharing, then derives final path, volume/file identity, file attributes/reparse metadata and owner/DACL rules from those handles. Fresh snapshots request read/security access and share read plus delete—but not write—so an atomic rename may publish while the snapshot handle remains bound to one complete old-or-new object; exact final path/security/object validation and pinned-directory revalidation remain mandatory before bytes return. Atomic writes create a cryptographically named same-parent share-zero stage, validate its handle/security, write, flush and read back exact bytes, and revalidate every held directory immediately before commit.

The corrected commit uses the documented Win32 absolute-path form: `SetFileInformationByHandle(FileRenameInfoEx)`, `RootDirectory == nullptr`, and the complete canonical allowlisted target rebuilt as `pinnedParent.finalPath + validatedBasename`. A colon in the basename is rejected so an NTFS stream name cannot enter this surface. The source is still the validated staged handle; no `MoveFile*`, `ReplaceFile*`, path fallback or NT/Zw API exists. The held root/parent handles deny delete sharing, and the staged file remains open share-zero. Microsoft documents both that `FILE_RENAME_INFO::FileName` may be absolute and that a directory cannot be renamed while it or a descendant contains an ordinary open handle; those rules prevent a directory-chain swap during the one rename operation. A fresh target handle must then match exact path, containment, staged volume/file ID, regular/non-reparse state, security and bytes, followed by another held-directory validation.
